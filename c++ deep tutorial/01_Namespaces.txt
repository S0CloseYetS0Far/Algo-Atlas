## Chapter Overview

Namespaces are a core C++ language feature used to organize code and avoid naming conflicts.
As a project grows, different libraries and modules are very likely to define functions, types,
or variables with the same name. Namespaces provide a logical grouping mechanism that lets
entities with the same name coexist in different namespaces without conflict.

This chapter starts from the compiler's low-level principles and explains in depth how namespaces
work in symbol table resolution, name mangling, and the linking process. It then thoroughly
covers all namespace-related syntax features and standard usage in C++, and finally consolidates
what we have learned through three real-life scenario case studies.

### Section 1: Basic Example Code + Low-Level Computer Principles
================================================================================

1.1 Basic Concepts of Namespaces and Example Code
-------------------------------------------------

The most basic use of a namespace is to define a scope with the namespace keyword, isolating the
identifiers inside it from the outside. Here is the most basic example:

```cpp
#include <iostream>

// Define namespace A
namespace A {
    int value = 10;

    void print() {
        std::cout << "A::print(), value = " << value << std::endl;
    }

    class Foo {
    public:
        void hello() {
            std::cout << "Hello from A::Foo" << std::endl;
        }
    };
}

// Define namespace B
namespace B {
    int value = 20;

    void print() {
        std::cout << "B::print(), value = " << value << std::endl;
    }

    class Foo {
    public:
        void hello() {
            std::cout << "Hello from B::Foo" << std::endl;
        }
    };
}

int main() {
    // Access namespace members using fully qualified names
    std::cout << "A::value = " << A::value << std::endl;
    std::cout << "B::value = " << B::value << std::endl;

    A::print();
    B::print();

    A::Foo fooA;
    B::Foo fooB;
    fooA.hello();
    fooB.hello();

    return 0;
}
```

In the code above, both namespaces A and B have members named value, print, and Foo. Without
namespaces, these identically named identifiers would cause compile errors (redefinition). With
the A:: and B:: prefixes (fully qualified names), the compiler can precisely tell which
namespace's entity is being used.

1.2 using Declarations and using Directives
-------------------------------------------

C++ provides two ways to simplify access to namespace members: the using declaration and the
using directive. Their scope and effects are completely different, and understanding the
difference is essential to using namespaces correctly.

```cpp
#include <iostream>

namespace Data {
    int x = 100;
    int y = 200;

    void display() {
        std::cout << "Data::display()" << std::endl;
    }

    void process() {
        std::cout << "Data::process()" << std::endl;
    }
}

namespace Extra {
    int x = 999;
}

int main() {
    // === 1. using declaration ===
    // Brings one specific member of a namespace into the current scope
    using Data::x;        // Bring Data::x into the current scope
    // using Extra::x;    // Error! Conflicts with the using Data::x above
    using Data::display;  // Bring Data::display into the current scope

    std::cout << "x = " << x << std::endl;   // Use x directly; it is actually Data::x
    display();                                // Use display() directly

    // === 2. using directive ===
    // Brings all members of an entire namespace into the current scope
    {
        using namespace Data;  // Bring all members of Data into this block scope
        std::cout << "y = " << y << std::endl;   // Use y directly
        process();                                // Use process() directly
    }
    // After leaving the scope, using namespace Data no longer applies

    // std::cout << "y = " << y << std::endl;  // Error! y is not declared

    return 0;
}
```

A using declaration (using Data::x) is like "introducing one specific person": it injects that
exact name into the current scope. A using directive (using namespace Data) is like "opening the
door to the whole room": it makes every name in that namespace visible in the current scope. If
an outer scope has an identifier with the same name, a using declaration in the local scope hides
the outer name; but if the outer scope already has a variable with the same name and you then use
a using directive to import a namespace containing a member with that name, ambiguity may result.

```cpp
#include <iostream>

namespace A { int x = 1; }
namespace B { int x = 2; }

int main() {
    using namespace A;
    using namespace B;

    // std::cout << x << std::endl;  // Compile error! x is ambiguous
    std::cout << "A::x = " << A::x << std::endl;
    std::cout << "B::x = " << B::x << std::endl;

    return 0;
}
```

When two namespaces are both opened with using directives and they contain members with the same
name, using that name directly is ambiguous. The compiler cannot tell which one you mean. In this
case you must use the fully qualified name to resolve the ambiguity.

1.3 Compiler Internals: Symbol Table Resolution
-----------------------------------------------

Now let's dig into the compiler's internals. When a C++ compiler processes source code, it
maintains a core data structure: the Symbol Table. The symbol table records information about
each identifier (variable names, function names, type names, etc.), including its name, type,
scope, storage location, and so on.

During compilation, when the compiler encounters a reference to an identifier (for example a call
to foo()), it performs Name Lookup, searching the symbol table from the current scope outward,
level by level, until it finds a matching declaration.

The role of namespaces in the symbol table mechanism: each namespace corresponds to an independent
scope entry in the symbol table. The compiler maintains a separate symbol sub-table for each
namespace (or one level in the scope stack). When a fully qualified name such as A::foo is used,
the compiler looks up foo directly in namespace A's symbol table, skipping the usual
inside-out name lookup process.

```cpp
// Logical sketch of the compiler's internal symbol table structure
//
// Global scope (::)
//   ├── namespace A
//   │     ├── int value    → address/offset
//   │     ├── void print() → function signature
//   │     └── class Foo    → class definition info
//   └── namespace B
//         ├── int value    → address/offset
//         ├── void print() → function signature
//         └── class Foo    → class definition info
//
// main function scope
//   └── (local variables, etc.)
```

The compiler uses a "two-level lookup" strategy. The first level is ordinary unqualified name
lookup, searching outward from the current scope; the second level is Argument-Dependent Lookup
(ADL), also known as Koenig lookup. When a function is called and an argument belongs to some
namespace, the compiler also automatically searches that namespace for the function.

```cpp
#include <iostream>

namespace Graphics {
    class Point {
    public:
        int x, y;
        Point(int a, int b) : x(a), y(b) {}
    };

    void draw(const Point& p) {
        std::cout << "Drawing Point(" << p.x << ", " << p.y << ")" << std::endl;
    }
}

int main() {
    Graphics::Point pt(10, 20);

    draw(pt);  // ADL: because pt is of type Graphics::Point,
               // the compiler automatically looks for draw in the Graphics namespace
               // No need to write Graphics::draw(pt)

    return 0;
}
```

This code compiles thanks to the ADL mechanism. Although draw is not qualified with the Graphics::
prefix, the type of the argument pt, Point, is defined in the Graphics namespace, so the compiler
additionally looks for draw in Graphics. This is why std::cout << "hello" works: operator<<
lives in the std namespace and is found through ADL.

1.4 Name Mangling
-----------------

C++ supports function overloading: multiple functions with the same name can exist in the same
scope as long as their parameter types or counts differ. To make this possible, the compiler must
generate a unique symbol name for each overloaded function. This process is called
Name Mangling.

Name Mangling combines a function's "natural" name (its name in the source code) with its type
information (parameter types, return type, enclosing namespace, class name, etc.) and encodes them
into a unique string. This string is the symbol that the Linker sees.

Different compilers use different Name Mangling schemes:
- GCC / Clang use the mangling rules of the Itanium C++ ABI
- MSVC uses its own scheme
- Different mangling makes it hard to link code from different compilers together (ABI incompatibility)

Take the following code as an example:

```cpp
namespace Outer {
    namespace Inner {
        void func(int a) { /* ... */ }
        double func(double a, double b) { return a + b; }
    }
}

int main() {
    Outer::Inner::func(42);
    Outer::Inner::func(3.14, 2.71);
    return 0;
}
```

After compiling with GCC, use the nm tool to view the symbols in the object file:

```bash
$ g++ -c example.cpp -o example.o
$ nm example.o                    # View all symbols
$ nm -C example.o                 # Use -C to demangle (restore readable names)
```

Under the Itanium ABI, the names of the two functions above in the symbol table look roughly like this:

```
Before mangling (names in the source code):
  void Outer::Inner::func(int)
  double Outer::Inner::func(double, double)

After Name Mangling:
  _ZN5Outer5Inner4funcEi          ← 1 int parameter, returns void
  _ZN5Outer5Inner4funcEdd         ← 2 double parameters, returns double
```

Let's break down the structure of this mangled name step by step (using _ZN5Outer5Inner4funcEi as an example):

```
_Z           → C++ symbol prefix (Itanium ABI convention)
N            → start of nested name
  5Outer     → 5-character identifier "Outer"
  5Inner     → 5-character identifier "Inner"
  4func      → 4-character identifier "func"
  E          → end of nested name
  i          → parameter type int (i is the short code for int)
```

For the second function, _ZN5Outer5Inner4funcEdd:
```
_Z N 5Outer 5Inner 4func E d d
                            ↑ ↑
                            │ └── second parameter double (d = double)
                            └──── first parameter double (d = double)
```

Encodings of common fundamental types in mangling:
- v  → void
- i  → int
- f  → float
- d  → double
- c  → char
- b  → bool
- l  → long
- P  → pointer prefix (Pointer)
- R  → reference prefix (Reference)

If the function is a class member function, the mangled name includes the class name and namespace information. For example:

```cpp
namespace NS {
    class MyClass {
    public:
        void method(int, double);
    };
}
// mangled: _ZN2NS7MyClass6methodEid
// _Z N 2NS 7MyClass 6method E i d
```

1.5 Namespace Symbols from the Linker's Perspective
---------------------------------------------------

The linker's job is to resolve symbol references and merge the code and data sections of the
various object files (.o files). At this stage, namespaces have completely "disappeared": the
compiler has already turned them into part of the mangled name.

From the linker's perspective:
- Global variables appear in the symbol table under their original name or a name with an underscore prefix
- C++ functions appear in the symbol table under their mangled names
- Namespaces are represented entirely by character sequences within the mangled name
- Two functions with the same name in different namespaces have different mangled names (because
  the namespace prefixes differ), so the linker treats them as completely different symbols

When a .o file references an external symbol (for example, it calls a function defined in another
translation unit), the linker scans all input object files looking for a matching symbol. If none
is found, it reports an "undefined reference" error; if multiple matching symbol definitions are
found, it reports a "multiple definition" error.

```cpp
// file_a.cpp
namespace N1 {
    void sayHello() {
        // implementation...
    }
}

// file_b.cpp
namespace N2 {
    void sayHello() {
        // a different implementation
    }
}

// Mangled name of N1::sayHello: _ZN2N18sayHelloEv
// Mangled name of N2::sayHello: _ZN2N28sayHelloEv
// The linker treats them as two different symbols; no conflict
```

This is the underlying essence of how namespaces prevent symbol conflicts: they simply add a unique
prefix encoding to symbol names. At the binary level, there is no real "namespace" structure.

1.6 The Compiler's Symbol Lookup Strategy: Two-Level Lookup
-----------------------------------------------------------

When the compiler encounters the following code:

```cpp
namespace A {
    class X {};
    void f(X) { /* ... */ }
}

int main() {
    A::X obj;
    f(obj);  // What happens here?
}
```

The compiler's lookup process has two steps:

Step 1: Ordinary unqualified name lookup
  Starting from the current scope (inside main), search outward level by level for the name f.
  No f inside main → no f in the global namespace either → ordinary lookup fails.

Step 2: Argument-dependent lookup (ADL / Koenig Lookup)
  Because the type of the argument obj is A::X, and A::X is defined in namespace A,
  the compiler adds namespace A to the search list and finds f(A::X) in A.
  Lookup succeeds.

This two-level lookup mechanism is why we don't have to write std::operator<<(std::cout, "hello")
when using std::cout << "hello". Because the type of std::cout, std::ostream, is in the std
namespace, and operator<< is also defined there, ADL finds it automatically.

1.7 Interaction Between Namespaces and Translation Units
-------------------------------------------------------

C++'s compilation model is "separate compilation": each .cpp file (translation unit) is compiled
independently into an object file. A namespace can be "opened" and "extended" in multiple
translation units. Declarations belonging to the same namespace can be
spread across different files:

```cpp
// header1.h
namespace MyLib {
    void funcA();
}

// header2.h
namespace MyLib {
    void funcB();
}

// Once these two headers are included by different .cpp files,
// together they make up the contents of the MyLib namespace.
// When the compiler builds the symbol table in each translation unit,
// the MyLib namespace contains two entities: funcA and funcB.
```

This means namespaces are "open": you can add new members to an existing namespace anywhere.
But this also leads to a problem: if global entities with the same name are defined in different
translation units (even through namespace extension), conflicts can still occur at link time.

### Section 2: Complete Guide to All Usages (Standard Library / Keywords / Functions)

This section comprehensively lists all namespace-related usages in C++, covering standard features from C++98 to C++17/20.

2.1 Namespace Definition (the namespace keyword)
------------------------------------------------

A namespace is a logical grouping mechanism designed to prevent name conflicts. Syntax:

```cpp
namespace name {
    // declarations and definitions
}
```

Example: basic namespace definition

```cpp
namespace Math {
    const double PI = 3.141592653589793;
    int add(int a, int b) { return a + b; }
    int subtract(int a, int b) { return a - b; }
}
// Usage: Math::add(3, 5), Math::PI
```

A namespace can be defined in multiple "fragments" (it is open):

```cpp
// First fragment
namespace Math {
    int add(int a, int b) { return a + b; }
}
// Second fragment - adds new members
namespace Math {
    int multiply(int a, int b) { return a * b; }
    int divide(int a, int b) { return b != 0 ? a / b : 0; }
}
// Now Math contains add, multiply, divide
```

2.2 Nested Namespaces
---------------------

Namespaces can be nested, forming a tree structure.

C++98/03 syntax:

```cpp
namespace Outer {
    namespace Inner {
        int value = 42;
        void func() { /* ... */ }
    }
}
// Access: Outer::Inner::value, Outer::Inner::func()
```

C++17 introduced a simplified syntax for nested namespaces (compact nesting):

```cpp
// New in C++17: define nested namespaces directly with ::
namespace Company::Project::Module {
    class Engine {
    public:
        void start() { /* ... */ }
    };
}
// Equivalent to:
// namespace Company {
//     namespace Project {
//         namespace Module {
//             class Engine { ... };
//         }
//     }
// }
// Access: Company::Project::Module::Engine

// C++20 supports inline nested namespaces
namespace A::inline B::C {
    // B is an inline namespace
    // Equivalent to:
    // namespace A {
    //     inline namespace B {
    //         namespace C { ... }
    //     }
    // }
}
```

Deep nesting example:

```cpp
#include <iostream>

namespace Web {
    namespace Server {
        namespace V1 {
            void handleRequest() {
                std::cout << "Handling request with V1 API" << std::endl;
            }
        }
        namespace V2 {
            void handleRequest() {
                std::cout << "Handling request with V2 API" << std::endl;
            }
        }
    }
}

int main() {
    Web::Server::V1::handleRequest();
    Web::Server::V2::handleRequest();
    return 0;
}
```

2.3 Unnamed (Anonymous) Namespaces
----------------------------------

A namespace with no name. In C++ it replaces the static keyword for giving entities internal
linkage within a translation unit.

```cpp
// Syntax: namespace { }  (no name)
namespace {
    int internal_counter = 0;
    void helperFunc() {
        ++internal_counter;
    }
    class InternalData {
    public:
        int id;
        InternalData() : id(internal_counter++) {}
    };
}

// Equivalent to (but not exactly):
// static int internal_counter = 0;
// static void helperFunc() { ++internal_counter; }

// Members of an anonymous namespace have internal linkage
// They can only be accessed within this translation unit (.cpp file)
// Other translation units cannot reference these symbols
```

The C++ standard recommends using anonymous namespaces instead of file-scope static declarations.
Class and type definitions in an anonymous namespace are also protected, which static cannot do
(static can only be applied to functions and variables).

Name Mangling for anonymous namespaces:

Although an anonymous namespace has no name, the compiler must generate a unique internal name for
it to ensure that anonymous-namespace symbols in different translation units don't conflict. GCC
typically uses a random string that includes the file name:

```
// Anonymous namespace in file_a.cpp
namespace { int secret = 10; }
// The mangled name might be: _ZN12_GLOBAL__N_16secretE

// Anonymous namespace in file_b.cpp
namespace { int secret = 20; }
// The mangled name might be: _ZN12_GLOBAL__N_27secretE
// Different random suffixes ensure the two symbols are distinct
```

2.4 Inline Namespaces (inline namespace, C++11)
-----------------------------------------------

Members of an inline namespace can be accessed directly through the enclosing namespace, as if
they were declared in the enclosing namespace itself. This is mainly used for versioning.

```cpp
#include <iostream>

namespace Library {
    // V1 is the current version, so make it inline
    inline namespace V1 {
        void process() {
            std::cout << "Library V1 process" << std::endl;
        }
    }

    // V2 is an old version, not inline
    namespace V2 {
        void process() {
            std::cout << "Library V2 process" << std::endl;
        }
    }
}

int main() {
    // Thanks to inline, members of V1 can be accessed directly via Library::
    Library::process();     // Calls V1::process! Same as Library::V1::process()

    // You can also specify the version explicitly
    Library::V1::process(); // Explicitly call V1
    Library::V2::process(); // Explicitly call V2

    return 0;
}
```

When the library is upgraded, you only need to move the inline keyword to the new version's
namespace to switch the default version smoothly, with no changes to existing code.

```cpp
namespace Library {
    namespace V1 {
        void process() { /* old implementation */ }
    }
    inline namespace V2 {   // Now V2 is the default version
        void process() { /* new implementation */ }
    }
}
// All Library::process() calls now automatically point to V2
```

ADL also works with inline namespaces: an inline namespace is treated as a direct part of the
enclosing namespace.

2.5 Namespace Alias
-------------------

Create a short alias for a long namespace name to improve code readability.

```cpp
// Syntax: namespace alias = namespace_name;

namespace VeryLongCompanyName {
    namespace SpecificProject {
        namespace CoreModule {
            class Engine {
            public:
                void run() { /* ... */ }
            };
        }
    }
}

// Create an alias to simplify access
namespace Core = VeryLongCompanyName::SpecificProject::CoreModule;

int main() {
    Core::Engine engine;
    engine.run();
    return 0;
}
```

Common use cases for namespace aliases:

```cpp
#include <iostream>

// Boost libraries often have very deep namespace hierarchies
// namespace fs = boost::filesystem;

// C++17 std::filesystem
namespace fs = std::filesystem;  // Simplify file system operations

// Choose between namespaces based on a condition
namespace LibA { void doWork() { std::cout << "LibA" << std::endl; } }
namespace LibB { void doWork() { std::cout << "LibB" << std::endl; } }

// Use an alias to switch implementations while the calling logic stays the same
namespace ActiveLib = LibA;  // Choose LibA

int main() {
    ActiveLib::doWork();  // Output: LibA
    return 0;
}
```

2.6 using Declarations
----------------------

Precisely brings one specific name from a namespace into the current scope.

```cpp
#include <iostream>
#include <string>

namespace Drawing {
    class Color {
    public:
        int r, g, b;
        Color(int red, int green, int blue) : r(red), g(green), b(blue) {}
    };

    std::string toString(const Color& c) {
        return "rgb(" + std::to_string(c.r) + "," +
               std::to_string(c.g) + "," + std::to_string(c.b) + ")";
    }

    void render() {
        std::cout << "Rendering..." << std::endl;
    }

    const int DEFAULT_WIDTH = 800;
    const int DEFAULT_HEIGHT = 600;
}

int main() {
    // Bring in the needed names one by one
    using Drawing::Color;         // Bring in a type
    using Drawing::toString;      // Bring in a function
    using Drawing::DEFAULT_WIDTH; // Bring in a constant

    Color c(255, 128, 64);        // Use Color directly
    std::cout << toString(c) << std::endl; // Use toString directly
    std::cout << "Width: " << DEFAULT_WIDTH << std::endl;

    // render was not brought in, so it still needs a fully qualified name
    // render();                   // Error!
    Drawing::render();            // Correct

    return 0;
}
```

A using declaration can be used in any scope: global scope, namespace scope, class scope (since
C++11 it can bring in base class constructors), function scope, and block scope.

Using a using declaration in a class (bringing in base class members):

```cpp
#include <iostream>

class Base {
public:
    void func(int x) {
        std::cout << "Base::func(int) : " << x << std::endl;
    }
    void func(double x) {
        std::cout << "Base::func(double) : " << x << std::endl;
    }
};

class Derived : public Base {
public:
    // Bring both of the base class's func overloads into the derived class scope
    using Base::func;

    // Add a new overload
    void func(const char* s) {
        std::cout << "Derived::func(const char*) : " << s << std::endl;
    }
};

int main() {
    Derived d;
    d.func(42);        // Calls Base::func(int)
    d.func(3.14);      // Calls Base::func(double)
    d.func("hello");   // Calls Derived::func(const char*)

    // Without using Base::func;, the derived class's func(const char*) would hide
    // all of the base class's func overloads, so d.func(42) and d.func(3.14) would not compile
    return 0;
}
```

2.7 using Directives
--------------------

Imports all names of an entire namespace into the current scope.

```cpp
#include <iostream>
#include <vector>
#include <string>

namespace Inventory {
    struct Item {
        std::string name;
        int quantity;
        double price;
    };

    double calculateTotal(const std::vector<Item>& items) {
        double total = 0.0;
        for (const auto& item : items) {
            total += item.quantity * item.price;
        }
        return total;
    }

    void printReport() {
        std::cout << "Inventory Report" << std::endl;
    }
}

int main() {
    using namespace std;        // Import the std namespace (common in demos; use with care in production code)
    using namespace Inventory;  // Import the Inventory namespace

    vector<Item> items = {
        {"Apple", 10, 1.5},
        {"Banana", 5, 2.0}
    };

    cout << "Total: " << calculateTotal(items) << endl;
    printReport();

    return 0;
}
```

Notes:
- Never write using namespace std; in a header file: it pollutes the namespace of every
  translation unit that includes that header.
- Using using namespace std; inside a function in a .cpp file is relatively safe.
- When multiple using directives are in effect and they bring in identically named identifiers, ambiguity may result.

2.9 Referring to the Global Namespace (::)
------------------------------------------

The :: prefix denotes the global namespace (sometimes called the global scope resolution operator).

```cpp
#include <iostream>

int value = 100;  // Global variable

namespace MyLib {
    int value = 200;  // value in MyLib

    void show() {
        int value = 300;  // Local variable

        std::cout << "Local value: " << value << std::endl;       // 300
        std::cout << "MyLib::value: " << MyLib::value << std::endl; // 200
        std::cout << "Global value: " << ::value << std::endl;     // 100
    }
}

int main() {
    MyLib::show();
    return 0;
}
```

A leading :: means "start the lookup from the global root namespace". This is especially useful when:
- A local variable hides a global variable
- Accessing global functions/variables from inside a namespace
- Accessing global functions from inside a class

```cpp
#include <iostream>

// Global function
void log(const char* msg) {
    std::cout << "[GLOBAL LOG] " << msg << std::endl;
}

namespace App {
    // Function inside the namespace
    void log(const char* msg) {
        std::cout << "[APP LOG] " << msg << std::endl;
    }

    void test() {
        log("from test");     // Calls App::log
        ::log("from test");   // Calls the global log; note the :: prefix
    }
}

int main() {
    App::test();
    return 0;
}
```

2.10 Separating Declaration and Definition in a Namespace
---------------------------------------------------------

Functions in a namespace can be declared first and defined later (even in different files):

```cpp
// ---- header.h ----
#ifndef MATHUTIL_H
#define MATHUTIL_H

namespace MathUtil {
    double square(double x);
    double cube(double x);
    int factorial(int n);
}

#endif

// ---- source.cpp ----
#include "header.h"

namespace MathUtil {
    double square(double x) {
        return x * x;
    }

    double cube(double x) {
        return x * x * x;
    }

    int factorial(int n) {
        if (n <= 1) return 1;
        return n * factorial(n - 1);
    }
}
// They can also be defined outside the namespace using fully qualified names:
// double MathUtil::square(double x) { return x * x; }
```

2.11 C++20 Modules and Their Relationship to Namespaces
-------------------------------------------------------

C++20 introduced the module system, which provides a new way to organize code. Modules and
namespaces are complementary:

```cpp
// C++20 module example (conceptual)
// export module MyLib.Core;

// export namespace MyLib {      // Export the contents of the namespace
//     export class Engine { ... };
//     export void start() { ... };
// }
```

Modules control the "visibility boundary" of code (which code is visible to the outside), while
namespaces handle "logical grouping" (avoiding name conflicts). Using both together is the recommended practice.

Case 1: Courier Company Parcel Management System
----------------------------------------------------------------

Real-life scenario: a courier company offers three delivery services: domestic, international,
and same-city express. Each service has its own shipping fee calculation rules and its own way of
printing waybills. The company needs a unified management system so that once a user picks a
delivery type, the corresponding calculation and printing functions are called automatically.

This case demonstrates: isolating same-named functions with namespaces, selectively bringing in members with using declarations, and namespace aliases.

```cpp
#include <iostream>
#include <string>
#include <iomanip>

// ============================================================
// Namespace 1: Domestic express
// ============================================================
namespace Domestic {
    const double BASE_RATE = 10.0;      // Base fee
    const double PER_KG_RATE = 2.0;     // Price per kg

    double calculateFee(double weight) {
        return BASE_RATE + weight * PER_KG_RATE;
    }

    void printLabel(const std::string& sender,
                    const std::string& receiver,
                    const std::string& address,
                    double weight) {
        std::cout << "========== Domestic Express Waybill ==========" << std::endl;
        std::cout << "Sender: " << sender << std::endl;
        std::cout << "Receiver: " << receiver << std::endl;
        std::cout << "Address: " << address << std::endl;
        std::cout << "Weight: " << weight << " kg" << std::endl;
        std::cout << "Shipping fee: ¥" << calculateFee(weight) << std::endl;
        std::cout << "==============================================" << std::endl;
    }
}

// ============================================================
// Namespace 2: International express
// ============================================================
namespace International {
    const double BASE_RATE = 100.0;     // Base fee (yuan)
    const double PER_KG_RATE = 15.0;    // Price per kg
    const double CUSTOMS_FEE = 50.0;    // Customs declaration fee

    double calculateFee(double weight) {
        return BASE_RATE + weight * PER_KG_RATE + CUSTOMS_FEE;
    }

    void printLabel(const std::string& sender,
                    const std::string& receiver,
                    const std::string& address,
                    double weight) {
        std::cout << "======= International Express Waybill =======" << std::endl;
        std::cout << "Sender: " << sender << std::endl;
        std::cout << "Receiver: " << receiver << std::endl;
        std::cout << "Address: " << address << std::endl;
        std::cout << "Weight: " << weight << " kg" << std::endl;
        std::cout << "Shipping Fee: ¥" << calculateFee(weight) << std::endl;
        std::cout << "=============================================" << std::endl;
    }
}

// ============================================================
// Namespace 3: Same-city express (LocalExpress)
// ============================================================
namespace LocalExpress {
    const double FLAT_RATE = 8.0;  // Same-city flat rate

    double calculateFee(double weight) {
        (void)weight;  // Same-city express ignores weight
        return FLAT_RATE;
    }

    void printLabel(const std::string& sender,
                    const std::string& receiver,
                    const std::string& address,
                    double weight) {
        std::cout << "========== Same-City Express Waybill ==========" << std::endl;
        std::cout << "Sender: " << sender << std::endl;
        std::cout << "Receiver: " << receiver << std::endl;
        std::cout << "Address: " << address << std::endl;
        std::cout << "Same-city flat rate: ¥" << FLAT_RATE << std::endl;
        std::cout << "===============================================" << std::endl;
    }
}

// Express dispatch system
namespace ExpressDispatch {
    // Use using declarations to selectively bring in commonly used functions
    using Domestic::calculateFee;     // Bring in a specific function (but don't rely on it)
    using International::calculateFee; // Note: this causes a conflict; you can't "using" both calculateFee functions at once

    // The right approach: use a namespace alias to shorten long names
    namespace Local = LocalExpress;

    void showMenu() {
        std::cout << "\n╔════════════════════════╗" << std::endl;
        std::cout << "║  Delivery Service Menu ║" << std::endl;
        std::cout << "╠════════════════════════╣" << std::endl;
        std::cout << "║  1. Domestic express   ║" << std::endl;
        std::cout << "║  2. International      ║" << std::endl;
        std::cout << "║  3. Same-city express  ║" << std::endl;
        std::cout << "║  0. Exit               ║" << std::endl;
        std::cout << "╚════════════════════════╝" << std::endl;
    }

    void processOrder(int choice,
                      const std::string& sender,
                      const std::string& receiver,
                      const std::string& address,
                      double weight) {
        switch (choice) {
            case 1:
                // Call with a fully qualified name to make clear which namespace's function is used
                Domestic::printLabel(sender, receiver, address, weight);
                break;
            case 2:
                International::printLabel(sender, receiver, address, weight);
                break;
            case 3:
                Local::printLabel(sender, receiver, address, weight);
                break;
            default:
                std::cout << "Invalid choice!" << std::endl;
                break;
        }
    }
}

int main() {
    // Demo: using a using declaration within a scope
    {
        using Domestic::calculateFee;
        std::cout << "Local test: domestic express fee for 3kg = ¥"
                  << calculateFee(3.0) << std::endl;
    }
    // After leaving the scope, the using declaration no longer applies

    {
        using International::calculateFee;
        std::cout << "Local test: international express fee for 3kg = ¥"
                  << calculateFee(3.0) << std::endl;
    }

    // Simulate user interaction
    ExpressDispatch::showMenu();

    // Simulate processing a few orders
    std::cout << "\n>>> User A chose domestic express:" << std::endl;
    ExpressDispatch::processOrder(1, "Zhang San", "Li Si", "XX Road, Chaoyang District, Beijing", 2.5);

    std::cout << "\n>>> User B chose international express:" << std::endl;
    ExpressDispatch::processOrder(2, "Wang Wu", "John Smith",
                                   "123 Main St, New York, USA", 3.0);

    std::cout << "\n>>> User C chose same-city express:" << std::endl;
    ExpressDispatch::processOrder(3, "Zhao Liu", "Qian Qi", "YY Road, Pudong New Area, Shanghai", 1.0);

    return 0;
}
```

When compiled and run, the output shows that the same-named functions (calculateFee, printLabel) in
the three namespaces each work independently. The ExpressDispatch namespace uses a namespace alias
(namespace Local = LocalExpress) to simplify references to a long namespace name. The code also
demonstrates the block-scope behavior of using declarations.


Case 2: Music Player Song Management
----------------------------------------------------------------

Real-life scenario: we are developing a music player that supports two audio formats, MP3 and FLAC.
The player's internal modules are layered by function and organized with nested namespaces. As the
product evolves, the playback interface has two implementations, v1 and v2, and must remain
backward compatible: v2 is used by default, but the old v1 interface can still be called explicitly.

This case demonstrates: nested namespaces, inline namespaces for version compatibility, and decoders for different formats.

```cpp
#include <iostream>
#include <string>
#include <vector>

// ============================================================
// Player namespace hierarchy
// player (root)
//   ├── audio (audio subsystem)
//   │     ├── mp3 (MP3 format)
//   │     └── flac (FLAC format)
//   └── ui (user interface)
// ============================================================

namespace player {
namespace audio {

    // MP3 decoding module
    namespace mp3 {
        struct SongInfo {
            std::string title;
            std::string artist;
            int duration;  // seconds
            int bitrate;   // kbps
        };

        void decode(const std::string& filename) {
            std::cout << "[MP3 decoder] Decoding: " << filename << std::endl;
            std::cout << "  Using Huffman entropy decoding + IMDCT transform..." << std::endl;
        }

        SongInfo parseMetadata(const std::string& filename) {
            std::cout << "[MP3] Parsing metadata: " << filename << std::endl;
            SongInfo info;
            info.title = filename;
            info.artist = "Unknown Artist";
            info.duration = 240;
            info.bitrate = 320;
            return info;
        }
    }  // namespace mp3

    // FLAC decoding module
    namespace flac {
        struct SongInfo {
            std::string title;
            std::string artist;
            int duration;
            int sampleRate;   // Hz
            int bitDepth;     // bits per sample
        };

        void decode(const std::string& filename) {
            std::cout << "[FLAC decoder] Decoding: " << filename << std::endl;
            std::cout << "  Using linear predictive coding (LPC) for lossless audio reconstruction..." << std::endl;
        }

        SongInfo parseMetadata(const std::string& filename) {
            std::cout << "[FLAC] Parsing metadata: " << filename << std::endl;
            SongInfo info;
            info.title = filename;
            info.artist = "Unknown Artist";
            info.duration = 300;
            info.sampleRate = 44100;
            info.bitDepth = 24;
            return info;
        }
    }  // namespace flac

}  // namespace audio

// User interface module (shows different ways to access nested namespaces)
namespace ui {

    void showNowPlaying(const std::string& song) {
        std::cout << "\n┌────────────────────────────┐" << std::endl;
        std::cout << "│ ♫ Now playing: " << song << std::endl;
        std::cout << "│ ████████████░░░░░░ 70%     │" << std::endl;
        std::cout << "└────────────────────────────┘" << std::endl;
    }
}

}  // namespace player

// ============================================================
// Versioning: use inline namespace for playback engine version compatibility
// ============================================================
namespace playerEngine {

    // V1 is the old version
    namespace V1 {
        void play(const std::string& file) {
            std::cout << "[Engine V1] Playing: " << file
                      << " (single-threaded decoding)" << std::endl;
        }
        void pause() {
            std::cout << "[Engine V1] Playback paused" << std::endl;
        }
        void stop() {
            std::cout << "[Engine V1] Playback stopped" << std::endl;
        }
    }

    // V2 is the new version, made inline: V2 is used by default
    inline namespace V2 {
        void play(const std::string& file) {
            std::cout << "[Engine V2] Playing: " << file
                      << " (multi-threaded parallel decoding)" << std::endl;
        }
        void pause() {
            std::cout << "[Engine V2] Playback paused (position saved)" << std::endl;
        }
        void stop() {
            std::cout << "[Engine V2] Playback stopped (buffers released)" << std::endl;
        }
        // V2 adds a seek feature
        void seek(double seconds) {
            std::cout << "[Engine V2] Seeking to: " << seconds << " s" << std::endl;
        }
    }
}

// Aliases for convenient access
namespace Audio = player::audio;
namespace UI = player::ui;

int main() {
    std::cout << "╔══════════════════════════════╗" << std::endl;
    std::cout << "║      Music Player v2.0       ║" << std::endl;
    std::cout << "╚══════════════════════════════╝\n" << std::endl;

    // 1. Load an MP3 song: access the nested namespace with fully qualified names
    {
        std::string song = "Yesterday.mp3";
        std::cout << "--- Loading MP3 song ---" << std::endl;
        player::audio::mp3::decode(song);
        auto info = player::audio::mp3::parseMetadata(song);
        std::cout << "  Song: " << info.title
                  << " | Bitrate: " << info.bitrate << " kbps"
                  << " | Duration: " << info.duration << "s" << std::endl;
    }

    // 2. Load a FLAC song: simplified with a namespace alias
    {
        std::string song = "Bohemian_Rhapsody.flac";
        std::cout << "\n--- Loading FLAC song ---" << std::endl;
        Audio::flac::decode(song);
        auto info = Audio::flac::parseMetadata(song);
        std::cout << "  Song: " << info.title
                  << " | Sample rate: " << info.sampleRate << " Hz"
                  << " | Bit depth: " << info.bitDepth << "bit"
                  << " | Duration: " << info.duration << "s" << std::endl;
    }

    // 3. Version compatibility demo: inline namespace at work
    {
        std::cout << "\n--- Playback engine test ---" << std::endl;

        // V2 is called by default (because V2 is inline)
        playerEngine::play("Bohemian_Rhapsody.flac");
        playerEngine::pause();
        playerEngine::seek(120.0);  // The seek added in V2 can be called directly
        playerEngine::stop();

        // Explicitly call V1 (the old version is still available)
        playerEngine::V1::play("Yesterday.mp3");
        playerEngine::V1::pause();
        playerEngine::V1::stop();
        // playerEngine::V1::seek(60.0);  // Error! V1 has no seek
    }

    // 4. UI display
    UI::showNowPlaying("Bohemian_Rhapsody");

    // 5. Demo of a using declaration for a nested namespace
    {
        using player::audio::mp3::decode;  // Bring in only the decode function
        decode("test_song.mp3");            // Use it directly
    }

    return 0;
}
```

Code structure notes:
- `player::audio::mp3` and `player::audio::flac` show a typical nested namespace organization
- `inline namespace V2` makes calls to `playerEngine::play()` automatically route to the V2 implementation
- `namespace Audio = player::audio` (an alias) greatly simplifies access to deeply nested namespaces
- `using player::audio::mp3::decode` shows how to precisely import a single function in a block scope


Case 3: Smart Home Device Control System
----------------------------------------------------------------

Real-life scenario: a smart home system controls devices such as lights and air conditioners in
different rooms. Internal implementation details (such as protocol handling for communicating with
hardware) are hidden with an anonymous namespace. Device types are defined with #define macros (a
first look at preprocessor concepts, setting the stage for Chapter 2). Namespace aliases simplify
access to multi-level namespaces.

```cpp
#include <iostream>
#include <string>
#include <vector>

// Device type macro definitions (a first look at the preprocessor; see Chapter 2 for details)
#define DEV_TYPE_LIGHT   1
#define DEV_TYPE_AC      2
#define DEV_TYPE_CURTAIN 3
#define DEV_TYPE_TV      4

// ============================================================
// Smart home namespaces
// SmartHome
//   ├── LivingRoom (living room)
//   ├── Bedroom (bedroom)
//   └── Kitchen (kitchen)
// ============================================================

namespace SmartHome {

    // Device base class
    struct Device {
        int id;
        int type;
        std::string name;
        bool isOn;

        Device(int i, int t, const std::string& n)
            : id(i), type(t), name(n), isOn(false) {}
    };

    namespace LivingRoom {
        Device light1(101, DEV_TYPE_LIGHT, "Living room main light");
        Device light2(102, DEV_TYPE_LIGHT, "Living room ambient light");
        Device ac(201, DEV_TYPE_AC, "Living room AC");
    }

    namespace Bedroom {
        Device light(103, DEV_TYPE_LIGHT, "Bedroom main light");
        Device ac(202, DEV_TYPE_AC, "Bedroom AC");
        Device curtain(301, DEV_TYPE_CURTAIN, "Bedroom curtain");
    }

    namespace Kitchen {
        Device light(104, DEV_TYPE_LIGHT, "Kitchen light");
        Device tv(401, DEV_TYPE_TV, "Kitchen small TV");
    }

}  // namespace SmartHome

// ============================================================
// Control center: hide internal implementation with an anonymous namespace
// ============================================================
namespace ControlCenter {

    // Anonymous namespace: internal helper functions, invisible to the outside
    namespace {
        // Simulate the low-level hardware communication protocol
        void sendCommandToHardware(int deviceId, int command) {
            // In a real project this would talk to the hardware via serial port, WiFi, etc.
            std::cout << "  [Hardware layer] Sending to device #" << deviceId
                      << " command: " << command << std::endl;
        }

        // Logging (internal use)
        void internalLog(const std::string& msg) {
            std::cout << "  [Internal log] " << msg << std::endl;
        }

        // Convert device type to a name
        const char* getTypeName(int type) {
            switch (type) {
                case DEV_TYPE_LIGHT:   return "Light";
                case DEV_TYPE_AC:      return "AC";
                case DEV_TYPE_CURTAIN: return "Curtain";
                case DEV_TYPE_TV:      return "TV";
                default:               return "Unknown";
            }
        }
    }  // end of anonymous namespace

    // Public interface: switch devices on and off
    void turnOn(SmartHome::Device& dev) {
        if (dev.isOn) {
            std::cout << "[Control center] " << dev.name << " is already on" << std::endl;
            return;
        }
        dev.isOn = true;
        internalLog(std::string("Turning on: ") + dev.name + " (" +
                    getTypeName(dev.type) + ")");
        sendCommandToHardware(dev.id, 1);  // 1 = turn-on command
        std::cout << "[Control center] √ " << dev.name << " -> on" << std::endl;
    }

    void turnOff(SmartHome::Device& dev) {
        if (!dev.isOn) {
            std::cout << "[Control center] " << dev.name << " is already off" << std::endl;
            return;
        }
        dev.isOn = false;
        internalLog(std::string("Turning off: ") + dev.name + " (" +
                    getTypeName(dev.type) + ")");
        sendCommandToHardware(dev.id, 0);  // 0 = turn-off command
        std::cout << "[Control center] √ " << dev.name << " -> off" << std::endl;
    }

    void showStatus(const SmartHome::Device& dev) {
        std::cout << "  [" << getTypeName(dev.type) << "] "
                  << dev.name << " (ID:" << dev.id << ") -> "
                  << (dev.isOn ? "ON" : "OFF") << std::endl;
    }
}  // namespace ControlCenter

// Namespace aliases to shorten long names
namespace LR = SmartHome::LivingRoom;
namespace BR = SmartHome::Bedroom;
namespace KT = SmartHome::Kitchen;
namespace CC = ControlCenter;

// ============================================================
// Scene modes: configure multiple devices with one action
// ============================================================
namespace SceneMode {
    void movieMode() {
        std::cout << "\n>>> Starting [Movie Mode]" << std::endl;
        CC::turnOff(LR::light1);
        CC::turnOff(LR::light2);
        CC::turnOn(LR::ac);  // Turn on the AC to stay comfortable
        CC::turnOff(KT::light);
        CC::turnOn(KT::tv);
    }

    void sleepMode() {
        std::cout << "\n>>> Starting [Sleep Mode]" << std::endl;
        CC::turnOff(BR::light);
        CC::turnOn(BR::ac);      // Set the AC to sleep mode
        CC::turnOn(BR::curtain); // Close the curtain
        CC::turnOff(LR::light1);
        CC::turnOff(LR::light2);
    }

    void awayMode() {
        std::cout << "\n>>> Starting [Away Mode]" << std::endl;
        // Turn off all devices
        CC::turnOff(LR::light1);
        CC::turnOff(LR::light2);
        CC::turnOff(LR::ac);
        CC::turnOff(BR::light);
        CC::turnOff(BR::ac);
        CC::turnOff(BR::curtain);
        CC::turnOff(KT::light);
        CC::turnOff(KT::tv);
    }
}

int main() {
    std::cout << "╔══════════════════════════════╗" << std::endl;
    std::cout << "║      Smart Home System       ║" << std::endl;
    std::cout << "╚══════════════════════════════╝\n" << std::endl;

    // Access devices through aliases: concise code
    std::cout << "=== Current device status ===" << std::endl;
    CC::showStatus(LR::light1);
    CC::showStatus(LR::light2);
    CC::showStatus(LR::ac);
    CC::showStatus(BR::light);
    CC::showStatus(BR::ac);
    CC::showStatus(BR::curtain);
    CC::showStatus(KT::light);
    CC::showStatus(KT::tv);

    // Manual control
    std::cout << "\n=== Manual control ===" << std::endl;
    CC::turnOn(LR::light1);
    CC::turnOn(LR::light2);
    CC::turnOn(BR::light);

    // Run a scene mode
    SceneMode::movieMode();

    std::cout << "\n=== Device status after Movie Mode ===" << std::endl;
    CC::showStatus(LR::light1);
    CC::showStatus(KT::tv);

    SceneMode::sleepMode();
    SceneMode::awayMode();

    std::cout << "\n=== Device status after Away Mode ===" << std::endl;
    CC::showStatus(LR::light1);
    CC::showStatus(BR::ac);

    return 0;
}
```

Key takeaways from Case 3:
- **Anonymous namespace** (inside ControlCenter): hides internal functions such as sendCommandToHardware,
  internalLog, and getTypeName so outside code cannot call them. The compiler generates a unique
  internal name for the anonymous namespace, ensuring safety across translation units.
- **Namespace alias**: `namespace LR = SmartHome::LivingRoom` greatly shortens the reference path,
  simplifying code from `SmartHome::LivingRoom::light1` to `LR::light1`.
- **Macro definitions**: macros such as #define DEV_TYPE_LIGHT 1 define device types. This is basic
  preprocessor usage, which will be covered in detail in Chapter 2.
- **Fully qualified names**: `SmartHome::Device&`, `ControlCenter::turnOn()`, etc. clearly
  identify which namespace a type or function belongs to.

Exercise: Hospital Management System
------------------------------------

**Scenario description**:
Design a hospital management system that simulates three departments: Outpatient, Inpatient,
and Pharmacy. Each department has some functions with the same name but different behavior.

**Requirements**:

1. Create three namespaces: Outpatient, Inpatient, Pharmacy.

2. Each namespace contains the following same-named functions:
   - `registerPatient(const std::string& name)` — register a patient
     * Outpatient: register an outpatient and assign an outpatient number (format: OP-0001)
     * Inpatient: register an inpatient and assign a bed number and admission number (format: IP-0001, Bed-01)
     * Pharmacy: register a patient picking up medicine and verify the prescription
   - `queryRecord(const std::string& id)` — look up a patient record
     * Each namespace queries its own record system
   - `generateBill(const std::string& id)` — generate a bill
     * Outpatient: registration fee + examination fee + medicine fee
     * Inpatient: days of stay × bed fee + treatment fee + medicine fee
     * Pharmacy: medicine unit price × quantity

3. Create a nested namespace `hospital::admin` to manage the hospital's shared configuration:
   - Global information such as the hospital name and address
   - A `getConfig(const std::string& key)` function for reading configuration

4. In the main function:
   - Use fully qualified names to distinguish calls to the same-named functions in the three namespaces
   - Use using declarations to selectively bring in the most frequently used functions
   - Demonstrate that when two using declarations bring same-named functions from different
     namespaces into the same scope, the result is ambiguous and must be resolved with fully qualified names

5. Optional enhancements (if you have time):
   - Create namespace aliases for outpatient/inpatient/pharmacy (e.g. namespace OP = Outpatient)
   - Add comments in the code explaining which namespace each function call corresponds to

**Reference solution skeleton** (structural hints only; you need to complete the implementation yourself):

```cpp
#include <iostream>
#include <string>
#include <vector>
#include <map>

// Nested namespace: shared administration
namespace hospital {
    namespace admin {
        // Shared configuration
        const std::string HOSPITAL_NAME = "XX City People's Hospital";
        const std::string HOSPITAL_ADDRESS = "No. 100, XX Road, XX City";

        std::string getConfig(const std::string& key) {
            std::map<std::string, std::string> config = {
                {"name", HOSPITAL_NAME},
                {"address", HOSPITAL_ADDRESS},
                {"emergency_phone", "120"},
                {"billing_system", "v2.1"}
            };
            auto it = config.find(key);
            return it != config.end() ? it->second : "Unknown config";
        }
    }
}

// Outpatient department
namespace Outpatient {
    // Stores outpatient information
    struct PatientRecord {
        std::string id;       // OP-0001
        std::string name;
        std::string department;
        double fee;           // Total fee
    };

    std::vector<PatientRecord> records;
    int patientCounter = 0;

    void registerPatient(const std::string& name) {
        patientCounter++;
        std::string id = "OP-" + std::to_string(patientCounter);
        while (id.length() < 7) {
            id.insert(3, "0");
        }

5.1 ADL (Argument-Dependent Lookup) in Depth
--------------------------------------------

ADL (Argument-Dependent Lookup), also known as Koenig lookup, is an important and often confusing
part of C++'s name lookup rules. It was briefly introduced in Section 1.3; here we explore it in depth.

**The complete ADL rules:**

When making an unqualified function call (i.e. the function name has no namespace qualifier in
front of it), the compiler searches for the function in the following namespaces:

1. The namespaces of all argument types
2. The namespaces of the base classes of the argument types
3. If an argument is a class template specialization, the namespaces of the template's type arguments are also searched

```cpp
#include <iostream>
#include <string>

// A tricky case demonstrating ADL
namespace N {
    struct S {};
    void f(S) { std::cout << "N::f(S)" << std::endl; }
    void g(S) { std::cout << "N::g(S)" << std::endl; }
}

namespace M {
    struct T : N::S {};  // Inherits from N::S
    void h(N::S) { std::cout << "M::h(N::S)" << std::endl; }
}

void f(N::S) { std::cout << "::f(N::S)" << std::endl; }  // Global function

int main() {
    N::S s;
    M::T t;

    f(s);  // ADL searches N (because the argument type N::S is in N)
           // Ordinary lookup also finds ::f
           // Both match → ambiguity → compile error!

    // The right approach: use fully qualified names to resolve the ambiguity
    N::f(s);   // Explicitly call N::f
    ::f(s);    // Explicitly call the global f

    g(t);  // ADL: the type of argument t is M::T, which inherits from N::S
           // ADL searches M (the namespace of T's type) and N (the namespace of base class S)
           // It finds N::g(S), because T can be implicitly converted to S
           // Output: N::g(S)

    return 0;
}
```

**Why does ADL exist?**

The classic motivation for ADL is to make operator overloading work naturally:

```cpp
#include <iostream>
#include <string>

int main() {
    std::string s = "Hello";

    // The ADL behind this line of code:
    std::cout << s << std::endl;

    // Equivalent to:
    // operator<<(std::cout, s)
    // operator<< is defined in the std namespace
    // Because the type of std::cout, std::ostream, is in std
    // and the type of s, std::string, is also in std,
    // ADL automatically finds operator<< in std

    // Without ADL, you would have to write:
    // std::operator<<(std::cout, s);
    // std::operator<<(std::cout, std::endl);

    return 0;
}
```

**The two sides of ADL: convenience vs. pitfalls**

```cpp
#include <iostream>
#include <algorithm>
#include <vector>

namespace Library {
    struct Container {
        std::vector<int> data;
    };

    void swap(Container& a, Container& b) {
        std::cout << "Library::swap (custom version)" << std::endl;
        a.data.swap(b.data);
    }
}

int main() {
    Library::Container c1, c2;

    // The recommended idiom (takes advantage of ADL):
    using std::swap;
    swap(c1, c2);  // ADL finds Library::swap → the custom version is preferred
    // If there is no custom swap, it falls back to std::swap

    // Wrong way:
    // std::swap(c1, c2);  // Forces std::swap, bypassing ADL
    //                       // May not be optimal (large containers may trigger deep copies)

    return 0;
}
```

The C++ standard library relies heavily on ADL; the std::swap idiom is the classic example. For
every class you write that needs an efficient swap operation, you should provide a non-member swap
function in its own namespace so that ADL can find it automatically.

5.2 Interaction Between Namespaces and Templates
------------------------------------------------

Namespaces and templates are both core C++ features, and there are some details worth noting when they are used together.

```cpp
#include <iostream>
#include <vector>
#include <typeinfo>

// Define same-named class templates in different namespaces
namespace A {
    template<typename T>
    class Wrapper {
    public:
        T value;
        Wrapper(T v) : value(v) {}
        void show() const {
            std::cout << "A::Wrapper<" << typeid(T).name()
                      << ">::value = " << value << std::endl;
        }
    };
}

namespace B {
    template<typename T>
    class Wrapper {
    public:
        T value;
        Wrapper(T v) : value(v) {}
        void show() const {
            std::cout << "B::Wrapper<" << typeid(T).name()
                      << ">::value = " << value << std::endl;
        }
    };
}

int main() {
    A::Wrapper<int> wa(42);
    B::Wrapper<int> wb(100);

    wa.show();
    wb.show();

    // Templates working with namespaces: specialization
    // Templates can be specialized within a namespace
    return 0;
}
```

**Template specialization in a namespace:**

```cpp
#include <iostream>

namespace MyLib {
    template<typename T>
    struct Traits {
        static const char* name() { return "unknown"; }
    };

    // Specializations (must be in the same namespace)
    template<>
    struct Traits<int> {
        static const char* name() { return "int"; }
    };

    template<>
    struct Traits<double> {
        static const char* name() { return "double"; }
    };
}

int main() {
    std::cout << MyLib::Traits<float>::name() << std::endl;   // unknown
    std::cout << MyLib::Traits<int>::name() << std::endl;     // int
    std::cout << MyLib::Traits<double>::name() << std::endl;  // double
    return 0;
}
```

**Two-Phase Lookup and namespaces:**

Name lookup in templates happens in two phases:
- Phase 1: when the template definition is parsed, names that don't depend on template parameters are looked up
- Phase 2: when the template is instantiated, names that depend on template parameters are looked up

```cpp
#include <iostream>

void print(int x) {
    std::cout << "Global print(int): " << x << std::endl;
}

namespace MySpace {
    struct Data { int info; };

    void print(const Data& d) {
        std::cout << "MySpace::print(Data): " << d.info << std::endl;
    }

    template<typename T>
    void process(T arg) {
        print(42);       // Phase 1 lookup: doesn't depend on T; finds the global print(int)
        print(arg);      // Phase 2 lookup: depends on T; decided only at instantiation
                         // If T=Data, ADL finds MySpace::print(Data)
    }
}

int main() {
    MySpace::Data d{999};
    MySpace::process(d);
    // Output:
    // Global print(int): 42          ← result of phase 1
    // MySpace::print(Data): 999    ← result of phase 2 ADL

    return 0;
}
```

5.3 Best Practices for Organizing Namespaces in Large Projects
--------------------------------------------------------------

**Principle 1: Mirror the directory structure with namespaces**

```cpp
// Directory: src/network/tcp/
// Header: src/network/tcp/connection.h

namespace company {
namespace project {
namespace network {
namespace tcp {

class Connection {
public:
    void connect(const std::string& host, int port);
    void disconnect();
    void send(const std::vector<char>& data);
    std::vector<char> receive();
};

} // namespace tcp
} // namespace network
} // namespace project
} // namespace company

// C++17 simplified form:
// namespace company::project::network::tcp { ... }
```

**Principle 2: Never write using namespace X; in a header file**

```cpp
// ❌ Wrong (header.h)
#pragma once
#include <string>
#include <vector>
using namespace std;  // Very bad! Pollutes every translation unit that includes this header

// ✅ Correct (header.h)
#pragma once
#include <string>
#include <vector>

namespace MyLib {
    // using declarations are fine inside a namespace
    using std::string;
    using std::vector;

    class DataStore {
    public:
        vector<string> getItems();  // Concise
    };
}
```

**Principle 3: Use anonymous namespaces for hidden, file-local implementation**

```cpp
// mylib.cpp
#include "mylib.h"

namespace MyLib {

    // Internal functions and data invisible to the outside
    namespace {
        // Cache
        std::map<int, std::string> cache;

        // Internal helper functions
        bool isValidId(int id) {
            return id > 0 && id < 1000000;
        }

        std::string generateKey(int id) {
            return "key_" + std::to_string(id);
        }

        // Internal type
        struct InternalStats {
            int cacheHits = 0;
            int cacheMisses = 0;
        };
        InternalStats stats;
    }

    // Public interface
    std::string query(int id) {
        if (!isValidId(id)) {
            throw std::invalid_argument("Invalid ID");
        }
        std::string key = generateKey(id);
        auto it = cache.find(key);
        if (it != cache.end()) {
            ++stats.cacheHits;
            return it->second;
        }
        ++stats.cacheMisses;
        // ... actual query logic
        return "";
    }

}  // namespace MyLib
```

**Principle 4: Use inline namespaces for version compatibility**

This is a technique used by the C++ standard library itself:

```cpp
// Simulating the version evolution of std::string
namespace std {
    inline namespace __cxx11 {
        class string { /* new C++11 implementation */ };
    }
    namespace __cxx98 {
        class string { /* old C++98 implementation */ };
    }
}
// std::string points to std::__cxx11::string by default
// but can be switched to std::__cxx98::string via build/linker options
```

**Principle 5: Improve readability with namespace aliases**

```cpp
// Define aliases together at the top of the .cpp file
namespace fs = std::filesystem;
namespace chrono = std::chrono;
namespace net = company::project::network;
namespace tcp = company::project::network::tcp;
namespace json = nlohmann;  // Third-party library

// If the C++17 nested syntax isn't enough, use traditional nesting
namespace myapp {
    namespace core { /* ... */ }
    namespace ui { /* ... */ }
    namespace data { /* ... */ }
}

// Expose them uniformly through aliases
namespace core = myapp::core;
namespace ui = myapp::ui;
namespace data = myapp::data;
```

5.4 using Declarations for Inheritance in Classes (In Depth)
------------------------------------------------------------

Since C++11, using declarations can be used not only with namespaces but also in classes to bring in
base class constructors and member functions:

```cpp
#include <iostream>
#include <string>

// The base class has several constructors
class Vehicle {
public:
    Vehicle() : speed_(0) {
        std::cout << "Vehicle()" << std::endl;
    }
    Vehicle(int s) : speed_(s) {
        std::cout << "Vehicle(" << s << ")" << std::endl;
    }
    Vehicle(const std::string& name, int s)
        : name_(name), speed_(s) {
        std::cout << "Vehicle(\"" << name_ << "\", " << speed_ << ")" << std::endl;
    }

    void drive() { std::cout << "Driving at " << speed_ << std::endl; }

protected:
    int speed_ = 0;
    std::string name_;
};

// Use a using declaration to inherit all of the base class's constructors
class Car : public Vehicle {
public:
    using Vehicle::Vehicle;  // Inherit all of Vehicle's constructors!

    // Add its own method
    void honk() { std::cout << "Beep beep!" << std::endl; }
};

// Use a using declaration to change the access level of base class members
class Base {
public:
    void pubMethod() { std::cout << "public" << std::endl; }
protected:
    void protMethod() { std::cout << "protected" << std::endl; }
private:
    void privMethod() { std::cout << "private" << std::endl; }
};

class Derived : private Base {  // Private inheritance
public:
    using Base::pubMethod;   // Promoted to public
    // using Base::protMethod; // Promoted to public (but only protected members are accessible)
    // using Base::privMethod; // Error! Cannot access private members of the base class
};

int main() {
    // Using the base class's constructors:
    Car c1;                       // Vehicle()
    Car c2(120);                  // Vehicle(120)
    Car c3("Tesla", 150);         // Vehicle("Tesla", 150)

    c1.drive();
    c3.drive();
    c3.honk();

    // Using the promoted access level:
    Derived d;
    d.pubMethod();   // OK! Despite private inheritance, the using declaration raised its access level
    // d.protMethod(); // Error! Cannot access Base's protected method through Derived

    return 0;
}
```

5.5 Cross-File Namespace Symbol Conflicts and How to Resolve Them
-----------------------------------------------------------------

When two independent third-party libraries define global functions with the same name in the global
namespace, a conflict can still occur at link time even if your own code uses namespaces. This is
because under C linkage rules (extern "C"), symbol names are not mangled.

```cpp
// library_a.cpp - third-party library A
extern "C" {
    void init() {
        // Initialization of library A
    }
}

// library_b.cpp - third-party library B
extern "C" {
    void init() {
        // Initialization of library B ← symbol conflict!
    }
}

// Solution 1: wrap them in namespaces (if the libraries are compiled as C++)
namespace LibA {
    void init() { /* ... */ }
}

namespace LibB {
    void init() { /* ... */ }
}

// Solution 2: load dynamically with dlopen/dlsym (Linux)
// void* handle_a = dlopen("liba.so", RTLD_LAZY);
// void (*init_a)() = (void(*)())dlsym(handle_a, "init");
// void* handle_b = dlopen("libb.so", RTLD_LAZY);
// void (*init_b)() = (void(*)())dlsym(handle_b, "init");

// Solution 3: rename symbols with objcopy --redefine-sym
// $ objcopy --redefine-sym init=liba_init library_a.o
// $ objcopy --redefine-sym init=libb_init library_b.o
```

5.6 The Relationship Between Namespaces and extern "C"
------------------------------------------------------

extern "C" tells the compiler to use the C language linkage specification (no name mangling). When
an extern "C" function is declared inside a C++ namespace, the function belongs to that namespace but uses C linkage:

```cpp
#include <iostream>

namespace Native {
    extern "C" {
        void c_func(int x) {
            std::cout << "Native::c_func(" << x << ")" << std::endl;
        }

        int c_add(int a, int b) {
            return a + b;
        }
    }
}

// The functions belong to the Native namespace (a C++-level scope)
// but use C linkage (symbol names are not mangled)

// In C code you cannot write Native::c_func(42)
// You can only write c_func(42) (because C has no namespaces)

int main() {
    Native::c_func(42);           // At the C++ level, use the fully qualified name
    int sum = Native::c_add(3, 5); // At the C++ level, use the fully qualified name

    // After compilation:
    // The symbol name of Native::c_func is just c_func (no mangling)
    // The symbol name of Native::c_add  is just c_add  (no mangling)

    // But if another extern "C" function also named c_func exists in another namespace:
    // namespace Other { extern "C" { void c_func(int); } }
    // this causes a link error! The two functions have the same C symbol name

    return 0;
}
```

This is a dangerous combination: extern "C" disables name mangling, so same-named extern "C"
functions in different namespaces conflict at link time.

5.7 Compiler Diagnostics: Observing How Namespaces Affect Symbols
-----------------------------------------------------------------

In experiments, you can use the following commands to closely observe how namespaces appear at the binary level:

```bash
# Create a test file containing several namespaces
cat > ns_test.cpp << 'EOF'
namespace A {
    void func(int) {}
    namespace B {
        void func(double) {}
    }
}
namespace A {
    namespace C {
        void func(char) {}
    }
}
void func(long) {}
EOF

# Compile without linking
g++ -c ns_test.cpp -o ns_test.o

# View the mangled names in the symbol table
nm ns_test.o

# Sample output:
# 0000000000000000 T _Z1funci       ← ::func(int)
# 000000000000000b T _Z1funcl       ← ::func(long)
# 0000000000000016 T _ZN1A4funcEd   ← A::func(double)... and so on
# 0000000000000021 T _ZN1A4funcEi   ← A::func(int)
# 0000000000000032 T _ZN1A1B4funcEd ← A::B::func(double)
# 000000000000002c T _ZN1A1C4funcEc ← A::C::func(char)

# View section information
objdump -h ns_test.o
```

These tools help you intuitively understand how the compiler encodes namespace information into symbol names.

### Chapter Summary
================================================================================

Key points of this chapter:

1. **Namespaces are a compile-time logical grouping mechanism** that, at link time, is entirely
   turned into prefix encoding in mangled names. Namespaces "don't exist" at the binary level; they are just part of the symbol name.

2. The difference between a **using declaration** (using N::name) and a **using directive** (using namespace N):
   - using declaration: precisely brings in a single name, like declaring an alias for that name
   - using directive: opens the "door" of the whole namespace, making all its names visible in the current scope

3. **Anonymous namespaces** provide file-local linkage (replacing C's static) and can also be used for type definitions.

4. **Inline namespaces** enable versioned selection of the default interface.

5. **Namespace aliases** (namespace Short = Long::Nested::Name) simplify access to deeply nested namespaces.

6. **ADL (argument-dependent lookup)** lets operator overloads and standard library functions work naturally, but it can
   also lead to unexpected function matches. Understanding ADL is essential knowledge for advanced C++ programming.

7. **Best practices**: never use using namespace in a header file; prefer fully qualified names;
   inside .cpp files, using declarations can be used where appropriate to simplify code.

In later chapters you will see how namespaces work together with features such as preprocessor macros (Chapter 2),
dynamic memory management (Chapter 3), classes and objects (Chapter 4), and templates (Chapter 8).

6.1 "Static Linking" of Namespaced Symbols

Once namespaces have been resolved at compile time, only mangled names take part in linking.
Understanding this helps explain several common questions:

**Question 1: Why can't the same function in the same namespace be defined in different .cpp files?**

```cpp
// file_a.cpp
namespace MyLib {
    void process() { /* implementation A */ }  // mangled: _ZN5MyLib7processEv
}

// file_b.cpp
namespace MyLib {
    void process() { /* implementation B */ }  // mangled: _ZN5MyLib7processEv
}
// Link error: multiple definition of 'MyLib::process()'
// The two translation units produced exactly the same mangled name
```

**Question 2: Why does it work with anonymous namespaces?**

```cpp
// file_a.cpp
namespace {
    void process() { /* implementation A */ }
    // mangled: _ZN12_GLOBAL__N_17processEv  (GCC)
}

// file_b.cpp
namespace {
    void process() { /* implementation B */ }
    // mangled: _ZN12_GLOBAL__N_27processEv  (GCC, different random suffix)
}
// Different mangled names → no conflict!
```

6.2 Namespace Visibility Control (Symbol Export)

When building shared libraries (.so / .dylib / .dll), symbol visibility is very important. GCC and Clang
support `__attribute__((visibility("default")))` to control which symbols are visible externally.

```cpp
// Hide all symbols by default and export only the symbols in the specified namespace

// Compiler option: -fvisibility=hidden

// Mark symbols in the namespace as visible
namespace MyPublicAPI {
    __attribute__((visibility("default")))
    void publicFunction();

    __attribute__((visibility("default")))
    class PublicClass {
    public:
        void method();
    };
}

// Simplified approach: use macros
#ifdef _WIN32
    #define API_EXPORT __declspec(dllexport)
    #define API_IMPORT __declspec(dllimport)
#else
    #define API_EXPORT __attribute__((visibility("default")))
    #define API_IMPORT
#endif

namespace MyLib {
    API_EXPORT void exportedFunc();
    void internalFunc();  // Hidden from the outside
}
```

This shows how namespaces and preprocessor macros (Chapter 2 material) work together in real projects.

6.3 Decoding Mangled Names with c++filt

When you see mangled names in object files or error messages, you can use tools to restore them:

```bash
# Decode with c++filt
$ echo '_ZN5Outer5Inner4funcEi' | c++filt
# Output: Outer::Inner::func(int)

$ echo '_ZNKSt6vectorIiSaIiEE4sizeEv' | c++filt
# Output: std::vector<int, std::allocator<int>>::size() const

# Decode the symbols of an entire object file
$ nm -C mylib.o | head -20

# Or run nm first, then c++filt
$ nm mylib.o | grep ' T ' | cut -d' ' -f3- | c++filt
```

6.4 Deep Namespace Nesting and Compiler Limits

The ANSI C++ standard does not explicitly specify a maximum nesting depth for namespaces, but compilers have
practical limits. Generally, going beyond 3-4 levels is not recommended. If you need a deeper hierarchy,
consider a flat naming convention or moving the deep parts into separate files.

```cpp
// ❌ Excessive nesting (hard to maintain)
namespace a::b::c::d::e::f::g {
    void func();
}
// Call: a::b::c::d::e::f::g::func();

// ✅ Reasonable nesting
namespace Company::Project::Module {
    void func();
}
// Call: Company::Project::Module::func();

// If you really need deep levels, flatten them with an alias
namespace PM = Company::Project::Module;
PM::func();
```

6.5 Internal Organization of the Standard Library's Namespaces

The C++ standard library also uses namespaces extensively to organize its code internally. Understanding the
standard library's structure helps you understand how large C++ projects are organized:

```
std                     ← standard namespace (visible to users)
├── __detail            ← implementation details (users shouldn't use directly)
├── placeholders        ← std::placeholders::_1, _2...
├── chrono              ← C++11 time library
├── filesystem          ← C++17 file system library
├── literals            ← user-defined literals
│   ├── string_literals ← e.g. "hello"s
│   ├── chrono_literals ← e.g. 5h + 30min
│   └── string_view_literals ← e.g. "hello"sv
├── ranges              ← C++20 ranges library
│   └── views           ← view adaptors
├── execution           ← C++17 execution policies
├── pmr                 ← C++17 polymorphic memory resources
└── regex_constants     ← regular expression constants
```

The standard library groups related functionality with nested namespaces and uses inline namespaces for
version management (e.g. std::__cxx11::string).

6.6 Interaction Between Namespaces and Dynamic Libraries (DLL/SO)

When C++ code exposes an interface through a dynamic library, the use of namespaces requires special attention to ABI compatibility:

```cpp
// mylib.h — header file of the dynamic library
#pragma once

#ifdef _WIN32
    #ifdef MYLIB_EXPORTS
        #define MYLIB_API __declspec(dllexport)
    #else
        #define MYLIB_API __declspec(dllimport)
    #endif
#else
    #define MYLIB_API __attribute__((visibility("default")))
#endif

namespace MyLib {

    // Exported class (used across the DLL boundary)
    class MYLIB_API Engine {
    public:
        Engine();
        virtual ~Engine();
        virtual void start() = 0;     // A pure virtual interface is safer
        virtual void stop() = 0;
        static Engine* create();      // Factory function
    };

    // Exported free functions
    MYLIB_API int getVersion();
    MYLIB_API const char* getLibraryName();

}  // namespace MyLib
```

Across dynamic library boundaries, using a pure virtual interface (Abstract Base Class + Factory) is safer than
exporting concrete classes directly, because it avoids ABI differences between compilers.

6.7 The Role of Namespaces in Template Metaprogramming

In template metaprogramming, namespaces are likewise used to organize and isolate type computations:

```cpp
#include <iostream>
#include <type_traits>

namespace meta {

    // Compile-time conditional selection
    template<bool Cond, typename T, typename F>
    struct conditional {
        using type = F;
    };

    template<typename T, typename F>
    struct conditional<true, T, F> {
        using type = T;
    };

    template<bool Cond, typename T, typename F>
    using conditional_t = typename conditional<Cond, T, F>::type;

    // Compile-time integer constant
    template<int N>
    struct int_constant {
        static constexpr int value = N;
    };

    // Type list
    template<typename... Types>
    struct type_list {};

    // Get the length of a type list
    template<typename List>
    struct length;

    template<typename... Types>
    struct length<type_list<Types...>>
        : int_constant<sizeof...(Types)> {};

}  // namespace meta

// The namespace isolates the metaprogramming tools, avoiding pollution of the global namespace
int main() {
    using meta::conditional_t;
    using meta::int_constant;
    using meta::type_list;

    // Compile-time conditional selection
    using T1 = conditional_t<(sizeof(int) > sizeof(short)), int, short>;
    static_assert(std::is_same_v<T1, int>, "should pick int");

    // Type list length
    using MyTypes = type_list<int, double, char, float>;
    constexpr int n = meta::length<MyTypes>::value;
    std::cout << "Type list length: " << n << std::endl;  // 4

    return 0;
}
```

6.8 Managing API Compatibility with Namespaces in Large Projects

```cpp
// api_v1.h
namespace MyAPI {
    namespace v1 {
        struct User {
            std::string name;
            int age;
        };

        User* createUser(const std::string& name, int age);
        void deleteUser(User* user);
        void setEmail(User* user, const std::string& email);  // present since v1
    }

    // Use the latest version by default (inline)
    inline namespace v2 {
        struct User {
            std::string name;
            int age;
            std::string email;  // field added in v2
        };

        User* createUser(const std::string& name, int age,
                        const std::string& email = "");
        void deleteUser(User* user);
        // User in v2 already contains email, so setEmail is no longer needed
    }
}

// Usage:
// MyAPI::createUser("Alice", 25, "alice@example.com") → uses v2
// MyAPI::v1::createUser("Bob", 30) → explicitly uses v1
```

With versioned namespace hierarchies, you can keep evolving an API while still providing backward compatibility.

6.9 An Experiment to Verify How the Compiler and Linker Handle Namespaces

Create a test to verify your understanding of how namespaces behave at the compile and link level:

```cpp
// experiment.cpp
#include <iostream>
#include <string>

// Namespace A
namespace A {
    int value = 1;
    void print(const std::string& prefix) {
        std::cout << prefix << "A::print, value=" << value << std::endl;
    }
}

// Namespace B
namespace B {
    int value = 2;
    void print(const std::string& prefix) {
        std::cout << prefix << "B::print, value=" << value << std::endl;
    }
}

// Global value and print
int value = 3;
void print(const std::string& prefix) {
    std::cout << prefix << "global print, value=" << value << std::endl;
}

int main() {
    std::cout << "Symbol table experiment start" << std::endl;

    // 1. Fully qualified call → the compiler jumps straight to the symbol in that namespace
    A::print("Fully qualified: ");   // Look up print directly in A → _ZN1A5printERKNSt7...
    B::print("Fully qualified: ");   // Look up print directly in B → _ZN1B5printERKNSt7...
    ::print("Fully qualified: ");    // Global print → _Z5printRKNSt7...

    // 2. using declaration → creates an alias in the current scope
    {
        using A::value;     // Bring A::value into the block scope
        std::cout << "using A::value = " << value << std::endl;  // 1
        // Here value refers to A::value (hiding the outer global value)
    }

    // 3. using directive → opens the whole namespace
    {
        using namespace B;  // Bring all of B's names into this block
        // print("using namespace");  // Ambiguous! There is a global print and B also has print
        B::print("Explicit: ");  // Use the fully qualified name to resolve the ambiguity
    }

    // 4. Observe the differences in name mangling
    // After compiling, view:
    // $ nm -C experiment.o | grep print
    // The output should show that print in different namespaces has different mangled names

    return 0;
}
```

Compile and observe:
```bash
# Compile to an object file
g++ -c experiment.cpp -o experiment.o

# View the symbols
nm -C experiment.o | grep -E "value|print"

# You'll see something like:
# 0000000000000000 D A::value          ← A's value
# 0000000000000004 D B::value          ← B's value
# 0000000000000008 D ::value           ← global value
# 0000000000000000 T A::print(...)     ← A's print
# 000000000000001b T B::print(...)     ← B's print
# 0000000000000036 T ::print(...)      ← global print
# They are completely independent entities in memory!
